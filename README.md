# Codex Pulse

English | [简体中文](README.zh-CN.md)

A macOS menu bar app for monitoring multiple Codex accounts and sending minimal requests at their server-reported quota reset times.

Repository: `codex-pulse`. App name: `Codex Pulse`. Swift package: `CodexPulse`.

## Current status

Protocol verification, a three-account management CLI, and the native menu bar app are implemented. The app displays accounts, five-hour and weekly quotas, server reset times, and query errors, with manual refresh. Automatic requests on launch and after resets, per-window deduplication, wake recovery, installation, launch at login, and DMG packaging are also implemented. iOS support remains planned. Account titles use real usernames retrieved dynamically from the profile endpoint and updated on refresh.

Phase 1 verification is complete: an independent Plus account was authenticated, its quotas were read, and one minimal request completed successfully. The official five-hour window rule is the implementation basis; no additional window experiment is required, and the originally planned post-reset experiment was canceled. See the [phase 1 verification notes](docs/phase-1-verification.md). GitHub `origin` is configured. As requested on October 2, 2026, subsequent changes are verified, committed with Chinese commit messages, and pushed automatically.

## Phase 1 verification

Requires macOS 14 or later, Swift 6 or later, and an installed Codex CLI. The protocol adapter was developed against JSON Schema generated by Codex CLI 0.158.0.

```bash
cd /Users/j/github_repo/codex-pulse
swift build
./scripts/test.sh
swift run codex-pulse-probe handshake
swift run codex-pulse-probe login
swift run codex-pulse-probe status
swift run codex-pulse-probe models
swift run codex-pulse-probe probe
```

`login` opens a browser for authentication. `probe` sends a real model request and consumes quota. Use `--model` to select a model from the model catalog; when omitted, the catalog's default model is used with its lowest supported reasoning effort and Standard speed.

After the first request completes, the program prints the report's absolute path. To diagnose behavior after a reset, run the following once the report's five-hour reset time has passed. This is optional and is not a development prerequisite:

```bash
swift run codex-pulse-probe verify-reset --report "<absolute path to the first report>"
```

Post-reset verification uses the original report's model and checks account identity. It sends no model request before the reset time, when quota permission is unknown, or when quota is exhausted. See the [phase 1 notes](docs/phase-1-verification.md) for the procedure and interpretation limits.

## Menu bar app

Install into Applications:

```bash
cd /Users/j/github_repo/codex-pulse
./scripts/install-app.sh
open "/Applications/Codex Pulse.app"
```

Launch at login is enabled by default on the installed app's first run, without opening the menu bar panel first. The switch reflects the actual system state. If approval is required, use the button that opens System Settings. Turning it off in the app or System Settings is respected across restarts and updates. Development copies do not apply this default, so a temporary app path is not registered. Quit the installed app before updating it.

Build a drag-and-drop installer:

```bash
./scripts/package-dmg.sh
```

The output is `.build/dist/Codex-Pulse-<version>.dmg`. Open it and drag the app into Applications. The image contains only the app and an Applications link, with no account credentials. Account data stays in the existing Application Support directory. See the [installation and launch-at-login notes](docs/phase-4-installation.md). The current ad-hoc signature is for local personal use; Developer ID signing and notarization have not been completed.

To run a development copy:

```bash
cd /Users/j/github_repo/codex-pulse
./scripts/build-app.sh
open ".build/app/Codex Pulse.app"
```

The app reads all three accounts on launch. Click its ECG-style menu bar icon to view results; the refresh button queries accounts concurrently. Failed queries retain the last successful quota snapshot, shown in gray with its timestamp. Missing quota windows remain unknown.

After reading quotas, the app sends one real minimal request for each eligible account that has not already been attempted in the current window. Further requests follow each account's server-reported five-hour reset time. Manual refresh rechecks scheduling but does not repeat a request in the same window. An account stops automatic requests when its weekly quota is exhausted or its windows are unknown. Restarting or waking the Mac restores the current schedule without sending catch-up requests for missed windows.

Account creation, deletion, login, and alias changes use the CLI below. Usernames come from a user-authorized, read-only internal profile endpoint. Profile failures retain the most recent name and display an error; quota queries are handled independently.

The SwiftUI app is built with Command Line Tools and produces a locally ad-hoc-signed `.app`. See the [phase 3 notes](docs/phase-3-menu-bar.md) for profile endpoint limitations and the [phase 4 notes](docs/phase-4-automatic-requests.md) for scheduling, verification, and failure recovery.

## Three-account management

```bash
swift run codex-pulse accounts add --name "Account 1"
swift run codex-pulse accounts list
swift run codex-pulse accounts login --id "<stable ID from the account list>"
swift run codex-pulse accounts status
swift run codex-pulse accounts rename --id "<ID>" --name "Work account"
swift run codex-pulse accounts remove --id "<ID>"
```

Each account ID maps to a fixed login directory; aliases can include Chinese characters. At most three accounts are supported. Adding an account only registers an entry; authentication requires browser interaction. `status` queries all accounts concurrently, preserving other accounts' results when one fails. Duplicate logins to the same server account are identified as sharing quota. These commands do not send model requests.

The current three accounts have been authenticated and queried concurrently: accounts 1 and 3 are Plus, and account 2 is confirmed as Free. The Free account currently returns no five-hour or weekly windows, so both remain unknown. Eligibility follows server permissions and available quota windows, without inventing quota values or reset times from the plan name.

`remove` deletes only the selected account's independent directory and credentials, retaining historical verification reports. Failed deletion remains marked as pending and can be retried. An existing `probe-1` login can be registered with `accounts add --id probe-1 --name "Account 1"` and reused. See the [phase 2 notes](docs/phase-2-account-management.md) for the workflow and live verification results.

## First-release goals

- Display all three accounts' five-hour and weekly quotas, reset times, and update times.
- Provide a menu bar app for account login, quota queries, display, and automatic request scheduling.
- Send one minimal request for eligible accounts on launch. This starts an inactive five-hour window; an existing window is not restarted.
- Schedule subsequent requests using server-reported five-hour reset times, stopping an account when its weekly quota is exhausted.
- Query again and restore scheduling after restart or wake, without catch-up requests for missed windows.

The [official usage guidance](https://help.openai.com/en/articles/20001516-managing-usage-with-gpt-6-astra-in-work-and-codex) states that the first Work/Codex message after the previous five-hour window ends starts the next window. Reading quota is not equivalent to starting a window, and minimal requests themselves consume quota. Scheduling uses the server's actual reset times.

## Technical direction

- macOS 14 or later, Swift 6, and SwiftUI.
- Use the local Codex CLI's app-server for quota queries and independent account management.
- Identify windows by server-reported durations and reset times, rather than assuming fixed meanings for `primary` and `secondary`.
- Automatic scheduling requires the app to be running, the Mac to be awake, and network access to be available.

## Account isolation

Each account uses an independent `CODEX_HOME`:

```text
~/Library/Application Support/CodexPulse/accounts/<account-id>/
```

Scheduling checkpoints are stored in `Application Support/CodexPulse/scheduling/<account-id>.json`. The latest automatic request report is at `verification/<account-id>/reports/automatic-latest.json`. These are local files and contain no tokens or raw responses.

The app authenticates within these independent directories. It does not read or modify the everyday Codex App's `~/.codex` credentials or global state. Account tokens, cookies, and authentication files must not enter Git, exported quota data, or logs.
